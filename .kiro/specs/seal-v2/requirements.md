
# SlopSeal v2: Requirements

**Relation to v1:** `.kiro/specs/seal/` is the v1 contract and stays unchanged. v2 adds requirements. Where a v2 requirement changes a v1 statement, the v2 requirement names the v1 statement it supersedes. v1 files are not edited.
**Format:** EARS (Easy Approach to Requirements Syntax).
**Requirement IDs:** `R-<area>-<n>`. Commit messages cite them, for example `feat(hooks): verdict-aware hook [R-G-1]`.

| Prefix | Area | Phase | Status |
|--------|------|-------|--------|
| `R-G-*` | Gate: the Kiro install hook | 1 (`feat/v2-hook`) | Specified below |
| `R-C-*` | Contract Check | 2 (`feat/v2-contract`) | Specified in section 2. Not implemented |
| `R-S-*` | Signing: Ed25519 seals behind an optional extra | 3 (not scheduled) | Reserved. Needs ADR-0004 before any code |

**Glossary**

- **Gate (`R-G`)**: the Kiro install hook. It runs `verify_install` for each pinned pip or npm package in an agent command.
- **Contract Check (`R-C`)**: Phase 2. It reads what a package really exports, statically, from the artifact the registry serves for one exact version, so that an intent check can answer PRESENT, ABSENT, or UNKNOWN. Specified in section 2. Not implemented.
- **Signing (`R-S`)**: Ed25519 seals behind the optional `slopseal[sign]` extra. Needs ADR-0004.
- **T17, T18, T23**: threats that Phase 2 addresses. T17 is a hostile artifact (archive bomb, path traversal, code run while the artifact is read). T18 is an artifact that builds its exports at run time to dodge the check. T23 is an artifact that does not match the digest the registry published. Mapped to R-C-1 to R-C-5. **Not implemented.** T19 to T22 are reserved for later phases and are not used in Phase 2.
- **T16**: transitive dependencies of a package that passes. Mapped to **R-G-12** (depth-1 transitive check). **Not implemented.** Phase 4 ships it. T16 stays open until then. R-G-4 is the QUARANTINE rule and does not cover transitive checks.

Terms used below:

- **Install** (for the hook): a simple command in the hook payload's `tool_input.command` that the v1 hook detects as an install. Detection is unchanged from v1.
- **Verifiable install**: an install that `slopseal.intercept.parse` turns into one or more registry packages, each at an exact version. That covers `pip install name==x.y.z`, `npm install name@x.y.z`, and `npx`, `npm exec`, `npm x` with `name@x.y.z`.
- **Unverifiable install**: any other install.

---

## 1. Gate: the verdict-aware install hook

**R-G-1 (verdict per package).** When the hook payload's `tool_input.command` contains a verifiable install, the system shall call `verify_install` once for each distinct package and exact version that the command names, without an intent. Each call is an install attempt for the rate limit (R-4.7).

**R-G-2 (ALLOW).** When every call under R-G-1 returns ALLOW and the command contains no unverifiable install, the system shall exit 0, so the command runs. The system shall write one summary line per package, and any warnings, to stderr.

**R-G-3 (BLOCK).** When any call under R-G-1 returns BLOCK, the system shall exit 2. For each blocked package the system shall write to stderr the package, the version, the failed check, the reason, and a suggested fix. The suggested fix is the check's remedy when it has one, and a fixed fallback text otherwise.

**R-G-4 (QUARANTINE).** When any call under R-G-1 returns QUARANTINE, the system shall exit 2. For each quarantined package the system shall write to stderr the package, the version, the check name (`mismatch_type`), the `quarantine_id`, and the next step.

**R-G-5 (unverifiable installs).** When the command contains an unverifiable install, the system shall exit 2 and write the reason and a suggested fix to stderr. Unverifiable includes: an unpinned name or a version range, a URL or local path, `-r` or another option that changes the source, a tool other than pip, npm, and npx, an install that names no package, packages supplied through `xargs`, an environment assignment before the install (it can redirect the index), and text the hook cannot parse. The system shall not resolve versions and shall not rewrite the command, because the hook can only allow or block the command it was given. R-1.7 does not apply to the hook.

**R-G-6 (fail closed).** If the hook cannot reach a decision, the system shall exit 2. That includes: an unreadable payload, a payload that does not close within the stdin timeout, a command that cannot be parsed, a policy, seal key, or snapshot error, an audit log that cannot be written, and a decision that does not finish within the hook deadline. When `tool_input.command` is missing or not a string, the system shall exit 2 for any install found in the payload, because it cannot know what will run.

**R-G-7 (non-install).** When the command contains no install, the system shall exit 0, shall call no verdict, shall write nothing to the audit log, and shall write nothing to stdout or stderr. This is the v1 behavior and it is unchanged. A setup failure on a non-install command does not change the exit code, because the hook does not load the pipeline for it. When the command contains an install and the pipeline cannot load or build, the system shall exit 2 (P-G-3).

**R-G-8 (exit codes and streams).** The hook shall exit with 0 or 2 only. Exit 0 is reached only through R-G-2 or R-G-7. The hook shall write nothing to stdout.

**R-G-9 (hook config).** The hook description in `.kiro/hooks/block-agent-installs.json` shall state the verdict behavior of R-G-2 to R-G-5. The packaged copy at `src/slopseal/hooks/block-agent-installs.json` shall stay identical to it (R-1.9). The `sh -c` wrapper that maps an exit code other than 0 or 2 to exit 2 shall stay.

**R-G-10 (untrusted metadata).** The system shall treat the text of a verdict reason as data. The hook shall write it as a JSON string value, never as prose that the agent could read as an instruction, and shall cap its length.

**R-G-12 (depth-1 transitive check). Not implemented. Planned for seal-v2 Phase 4.** When the hook or the PATH shim verifies a pinned install that passes R-G-1 to R-G-4, the system shall also check the direct dependencies of that exact version, one level deep, with the same L1 checks, and shall block the install if a dependency fails a check. Until Phase 4 ships this requirement, the hook and the shim do not check transitive dependencies, and T16 is open. This wording is provisional. Phase 4 writes the design and the properties before any code. R-G-4 is unchanged.

**R-G-11 (one count per install across layers).** When the hook and the PATH shim both verify the same exact package and version, the rate limit (R-4.7) shall count that install once. The hook always counts its own attempt. When the hook allows a package, it leaves one credit for that package and version. A shim attempt for the same package and version consumes one credit and does not count again, and the shim still runs the verdict pipeline. A credit expires after the 60-second window. A shim run after that window counts as a new install. The install key is the ecosystem, the normalized name, and the exact version. The shim cannot see the hook's command ID, because the hook payload has no ID that reaches the shim. This refines R-4.7 for the one case where a single install produces two attempts. The limit of 10 per minute (`max_installs_per_minute`) is unchanged. Fail closed: an unreadable rate-limit state still blocks (R-4.7).

## 2. Contract Check (Phase 2, not implemented)

**Purpose.** In live mode the registries do not publish exported symbols, so `exports()` returns nothing and every intent check blocks (R-Q-2). The Contract Check reads the exports from the artifact itself, statically, so that an intent check can answer PRESENT, ABSENT, or UNKNOWN. Offline mode is unchanged: it still reads the checksummed snapshot.

**Status.** Nothing in this section is implemented. No document may describe it as working before Phase 2 ships.

Terms used below:

- **Artifact**: the file the registry serves for one exact version. For PyPI, one wheel. For npm, the tarball.
- **Contract**: the set of export names read from an artifact. A contract is **complete** only when every file that could add an export was read and resolved. A contract that is not complete is never used to say a symbol is absent.
- **Intent check result**: PRESENT, ABSENT, or UNKNOWN (R-C-5).
- **Typed reason**: the label an UNKNOWN carries. It is one of seven: `sdist_only`, `dynamic_exports`, `limit`, `parse_error`, `network`, `no_digest`, `not_in_snapshot`. Each reason has one meaning. `parse_error` means the artifact's content could not be read, or that the ecosystem has no extraction, so the artifact is not read at all. `network` means the download or metadata request failed, timed out, was refused, or was redirected to a host outside the allowlist. `no_digest` means the registry published no usable digest. `not_in_snapshot` means the offline snapshot does not cover the package or version. No cause is reported under another reason's label. `dynamic_exports` means a statement that can change an export is not one of the modelled forms of the completeness rule (section 2).
- **Names**: the contract holds each export under two forms. The qualified form is `module.symbol` (for PyPI the dotted module path, for npm the import specifier). The bare form is the symbol alone, for symbols exported at the top level of the package. Each module's dotted path is also an export name.

**R-C-1 (static only, digest verified).** When the Contract Check needs the exports of an exact version in live mode, the system shall download the artifact the registry names for that version into a private temporary directory, verify its digest against the digest the registry published for that file, and only then open it. The system shall read the artifact statically. The system shall not import, execute, or run any code from the artifact, and shall not run an install script, a hook, or a build step. The digest is read as follows:

- PyPI: the `sha256` value in `urls[].digests` of the chosen file.
- npm: `dist.integrity`, a Subresource Integrity string. The system shall use the algorithm named in the string and shall not assume sha256. It accepts `sha512`, `sha384`, and `sha256`. When the string lists several, it uses the strongest.

If the registry publishes no usable digest, the system shall return UNKNOWN with reason `no_digest`. That covers a missing digest, an npm version with only the sha1 `shasum`, an unsupported algorithm, and a malformed value. The system shall not trust sha1. If the computed digest differs from the published digest, the system shall return BLOCK (check `contract_digest`, level HARD_BLOCK), never UNKNOWN (T23). The artifact URL shall use https and a host on the allowlist for the ecosystem (`files.pythonhosted.org` for PyPI, `registry.npmjs.org` for npm), including after a redirect. Any other host is UNKNOWN with reason `network`.

**Completeness rule (opt-in; applies to R-C-2, R-C-3, and R-C-5).** An extraction is complete only when every statement that can define or change an export matches a form this spec models. Any statement that writes to exports and is not modelled gives UNKNOWN with reason `dynamic_exports`. Over-flagging costs coverage only. Under-flagging can give a false ABSENT, which stops the phase. The modelled forms are:

- Python: a top-level `def`, `class`, simple name assignment (`name = expr`, `name: type = expr`, and chained `a = b = expr` with plain names), an import binding, and a literal `__all__`.
- ESM: `export { ... }` (with or without `from "<relative path>"`), `export const`, `let`, `var`, `function`, or `class`, `export default`, and `export * from "<relative path>"`, resolved one hop.
- CommonJS: `exports.x = ...`, `module.exports.x = ...`, and `module.exports = { ... }` whose entries are plain keys or shorthand keys. `Object.defineProperty(exports, "__esModule", ...)` is ignored.

Everything else that touches exports gives UNKNOWN.

**R-C-2 (Python exports).** When the artifact is for PyPI, the system shall use a wheel. If the version has only an sdist, the system shall return UNKNOWN with reason `sdist_only` and shall not download the sdist. When several wheels exist, the system shall choose a `none-any` wheel, and otherwise the first wheel filename in ascending byte order. The system shall find importable modules from the wheel's `RECORD` file and its top-level layout, and shall ignore `*.dist-info/` and `*.data/` entries other than purelib and platlib content. A wheel with no `RECORD`, or with a layout the system does not handle, is UNKNOWN with reason `parse_error`. The system shall parse each `.py` and `.pyi` file with `ast` and shall collect, per module, the union of two sets:

- Set A: the names in `__all__`, when `__all__` is the target of a plain or annotated assignment of a literal list or tuple of strings. Any other load of `__all__` gives UNKNOWN with reason `dynamic_exports`: an alias, `+=`, `.extend`, `.append`, passing `__all__` to a call, or a computed value. A literal addition is therefore not read, and it gives UNKNOWN.
- Set B: the public top-level names bound by modelled forms: `def`, `async def`, `class`, simple name assignments, and `import` and `from ... import ... [as ...]` bindings (the bound name is the alias, and `import a.b` binds `a`). A name that starts with an underscore is not in set B. The bindings above count inside module-level `if` and `try` blocks. Every branch counts: the `if`, `elif`, and `else` bodies, and the `try`, `except`, `else`, and `finally` bodies. Nested `if` and `try` blocks are walked the same way. The names from every branch are unioned, so a branch that is never taken can add a name. That can only cause a wrong PRESENT, which is reported. It cannot cause a false ABSENT. A module-level `for`, `with`, or `while` block, and a tuple target at module level, are unmodelled and give UNKNOWN (`dynamic_exports`). That is the setting for the first run. The owner may model them later.

A name in set A is exported even when it starts with an underscore.

The system shall follow `from .x import y` re-exports one hop, and `from .x import *` by reading the exports of `x` once. A star import whose target is outside the artifact, or a second hop, makes the result UNKNOWN with reason `dynamic_exports`.

The Python completeness check walks the whole file, including function bodies, and gives UNKNOWN with reason `dynamic_exports` when it finds any of the following. A reference to `exec`, `eval`, `setattr`, `globals`, `vars`, `sys.modules`, or `__dict__` counts as a reference, not only as a write, because aliasing is a write (Q1). A `global` statement. A `del` of a module name. A module-level `def __getattr__` or `def __dir__`. A `for`, `with`, or `while` block at module level, or a tuple target at module level. An augmented assignment to a module name. Any load of `__all__` other than the target of a plain or annotated literal assignment: an alias, `+=`, `.extend`, `.append`, passing `__all__` to a call, or a computed value. A file that does not parse is UNKNOWN with reason `parse_error`. A name in the contract longer than 256 characters, or containing whitespace or a control character, is UNKNOWN with reason `parse_error`.

**False-PRESENT risk of the union (documented, not a stop).** A name in set A or set B can be reported PRESENT when the module does not bind it at run time. The example is a name in `__all__` that the module never defines, or a public import inside an `if` block whose branch never runs. A wrong PRESENT is reported and does not stop the phase (P-C-4). Deleting a name is UNKNOWN under the completeness check, so a deleted name no longer adds to this risk. A false ABSENT needs a name that is bound at run time and is in neither set. The completeness check is designed to make that rare.

**Module-level `if` and `try` (R-C-2).** The walk enters every branch of a module-level `if` (the `if`, `elif`, and `else` bodies) and every branch of a module-level `try` (the body, each `except`, `else`, and `finally`), nested or not, and unions the names from all of them. A name bound only in an `except ImportError:` branch is therefore PRESENT, never ABSENT. Any other module-level statement that is not one of the modelled forms gives UNKNOWN with reason `dynamic_exports`, including `match`, a walrus assignment anywhere in the file, and a `for`, `while`, or `with` block at module level.

**Dynamic forms of the first run (R-C-2, confirmed at the 2.6 ruling).** The following give UNKNOWN with reason `dynamic_exports` for the whole artifact: a reference to `sys.modules` or to any attribute named `modules`; a reference to `__dict__` on any object; `from sys import modules`; a walrus assignment; a `match` statement; any module-level statement that is not modelled; any `global` statement in a module file. The `global` rule as ruled names a public name. The implementation flags every `global` statement in a module file, including one that names only a private name. That is stricter and costs coverage only.

**Compiled extensions (R-C-2, first run).** A compiled extension module (`.so` or `.pyd`) in the installed tree of a wheel gives UNKNOWN with reason `dynamic_exports` for the whole artifact. Its names are not read. The coverage cost is recorded in `docs/CONTRACT_EVAL.md`. The rule is not narrowed before the measurement.

**RECORD (R-C-2).** A `.py` or `.pyi` file in the installed tree that the wheel's `RECORD` does not list, a `RECORD` entry for a `.py` or `.pyi` file that the wheel does not contain, and a wheel with no importable module each give UNKNOWN with reason `parse_error`. Every wheel that gives `parse_error` for this reason is listed in the run report of 2.14.

**False-PRESENT risk (R-C-2, documented).** `from .x import y` binds `y` in the module that imports it, and the extractor does not read `x`. If `x` does not define `y` at run time, `y` is reported PRESENT. This cannot cause a false ABSENT. It is recorded as a false-PRESENT risk in `docs/CONTRACT_EVAL.md` and is reported, not a stop.

**R-C-3 (npm exports).** When the artifact is for npm, the system shall read `package.json` from the tarball at the root that the archive check selected (R-C-4), and it shall read each entry file from the tarball, never from disk. It uses the fields `exports`, `main`, `module`, `types`, `typings`, and `typesVersions`.

*Entry points.*

- With `exports` present, a string is the root entry. An object whose keys all start with `.` maps literal subpaths (`./sub`) to targets. An object whose keys do not start with `.` gives conditions for the root entry. A key that contains `*` (a pattern), a `typesVersions` field, and any condition key other than `import`, `require`, `node`, `default`, and `types` each give UNKNOWN with reason `dynamic_exports`. A `null` target is skipped. An array is a fallback list, and each element is read as a target. Each leaf string is one entry. A leaf with the extension `.js`, `.cjs`, or `.mjs` is a JavaScript entry. A leaf with the extension `.d.ts`, `.d.mts`, or `.d.cts` is a declaration entry. Any other leaf extension gives UNKNOWN with reason `dynamic_exports`. Entries are de-duplicated by resolved path.
- With `exports` absent, the entries are `module` (JavaScript), `main` (JavaScript), and `types` or `typings` (declaration), each when it is a string. When none of them is present, the entry is `index.js`.
- **Extensionless paths (ruled at the 2.14 review).** A `main` or `module` path with no extension is resolved as Node does, by probing in a fixed order. The first file that exists in the tarball is the entry: `<path>.js`, then `<path>.cjs`, then `<path>.mjs`. A `types` or `typings` path with no extension is probed as `<path>.d.ts` only, so that a type path never resolves to a JavaScript file. The path as written is not probed, because a file with no extension is neither a JavaScript nor a declaration leaf. A directory is not probed, so a `main` that names a directory gives UNKNOWN with reason `parse_error`. No probe finds a file gives UNKNOWN with reason `parse_error`. Extensionless `exports` leaves are not resolved and still give `dynamic_exports`.
- A declared entry that is not in the tarball gives UNKNOWN with reason `parse_error`. An entry path that is absolute, has a `..` segment, or contains a backslash or a NUL byte gives UNKNOWN with reason `parse_error`.

*Names.* The qualified form of a name is `<specifier>.<symbol>`, emitted for every entry, where the specifier is the package name for the root entry and `<name>/<subpath>` for a literal subpath. The bare form, the symbol alone, is emitted for the root entry only. A symbol of a subpath therefore has its qualified form only, so a claim on it as `<name>/<subpath>.<symbol>` is PRESENT, and a bare claim is ABSENT, which is correct for the root package. The qualified form is emitted for a scoped package too. Without it, a subpath symbol could never be PRESENT: a false ABSENT. The specifier is also an export name. The union is capped as in R-C-2.

*Completeness of each JavaScript entry.*

- **Accounted-for rule.** Every identifier token `exports` or `module` in a JavaScript entry must be part of one of the modelled statements below. Any other occurrence gives UNKNOWN with reason `dynamic_exports`. A `this` at the top level of a JavaScript entry, outside any brace block, is also an unaccounted occurrence: in a CommonJS module it is `module.exports`, so `this.name = value` exports a name. A `this` inside a function or a class is not counted. This rule is conservative and was added at the 2.8 step. A `this` inside a top-level block is not caught, and that gap is recorded in `docs/CONTRACT_EVAL.md`. Occurrences inside comments, strings, and regular expression literals are not tokens. An occurrence inside a template substitution `${...}` is a token.
- **Tokenizer.** The entry is tokenized with comments, string literals, template literals (with `${}` substitutions), and regular expression literals recognized. An unterminated string, template, regular expression, or block comment gives UNKNOWN with reason `parse_error`. A `/` that could be a regular expression or a division is decided from the previous token: after an identifier that is not a keyword, a number, a string, a template end, a regular expression, a `]`, or a `++` or `--`, it is a division. After a keyword such as `return`, `typeof`, `in`, `of`, `case`, or `yield`, and after an operator or punctuator other than `)`, `]`, and `}`, it is a regular expression. After a `)`, the keyword before the matching `(` decides it: `if`, `while`, `for`, and `with` give a regular expression, and any other token gives a division. After a `}`, the case cannot be resolved, so a `/` there gives UNKNOWN with reason `parse_error`.
- **Modelled CommonJS forms (Q2, Q3, Q4, Q5).** `exports.<name> = <expr>` and `module.exports.<name> = <expr>`, with `<name>` a plain identifier, including chained forms such as `exports.a = exports.b = void 0`. `module.exports = { ... }` where the literal has only plain keys (an identifier or a string) with values, or shorthand identifiers. A value may be any expression that contains no `exports` or `module` token. `Object.defineProperty(exports, "__esModule", ...)` is ignored. The name `default` is added by `exports.default = ...` (Q4) and by `export default` (Q4), and by no other rule.
- **Modelled ESM forms.** `export { a, b as c }`, optionally `from "./<relative path>"`. `export const`, `let`, or `var` with one identifier declarator. `export function` or `export class` with an identifier, including `async function` and `function*`. `export default`. `export * from "./<relative path>"`, resolved one hop. An `as default` rename in an export list, an `export * as`, a bare-package `from`, and any other `export` form give UNKNOWN with reason `dynamic_exports`.
- **Every other form gives UNKNOWN with reason `dynamic_exports`.** This includes `module.exports = <anything that is not a plain object literal>` (Q2, Q3); `exports = ...`; a read such as `module.exports.x` without `=`; `exports[...]`; a computed key, a spread, a method, an accessor, a numeric key, or a key named `default` in a `module.exports` literal; `typeof module`; `Object.assign(module.exports, ...)`; `Object.defineProperty` with any name other than `__esModule`, including a getter with a literal name (Q5); and the helpers `__export(`, `__exportStar(`, `__reExport(`, and `__createBinding(` (Q5). A `default` listed in an object literal or as an `as default` rename is not a rule that adds `default`, so it gives UNKNOWN and not a listing.

*Completeness of each declaration entry.*

- `export = <anything>` gives UNKNOWN with reason `dynamic_exports` (Q3). A `declare module` block gives UNKNOWN. `export as namespace` gives UNKNOWN.
- Modelled: `export` followed by an optional `declare`, then `const enum`, `enum`, `const`, `let`, `var`, `function`, `class`, `abstract class`, `interface`, `type`, or `namespace`, then an identifier. `export { a as b }`, optionally `from "./<relative path>"`. `export * from "./<relative path>"`, resolved one hop. `export default`, which adds `default` (Q4).
- Any other `export` form gives UNKNOWN with reason `dynamic_exports`.

*Two entry points (ruled at 2.6).* When a package resolves to more than one entry point (for example an `import` and a `require` entry, or a JavaScript entry and a declaration entry), a symbol is PRESENT when it is in any complete entry point. It is ABSENT only when every resolved entry point is complete and none lists it. Otherwise it is UNKNOWN with reason `dynamic_exports`. When every entry is complete, the contract is their union and is complete. When some entries are complete and some are not, the names of the complete entries are kept, and a symbol listed there is PRESENT. This is the one case in which a symbol of an incomplete contract is PRESENT (R-C-5). A symbol that the complete entries do not list is UNKNOWN, never ABSENT. When no entry is complete, the reason is the entry's reason when there is one entry, and `dynamic_exports` otherwise.

*Limits.* The entry files are read under the limits of R-C-4. A file over 5 MB is UNKNOWN with reason `limit`. The worker runs the extraction under the shared wall limit of R-C-4.

The name `default` is reserved (Q4). A claim on `default` is PRESENT when it is listed, and ABSENT only when the extraction is complete and it is not listed.

**R-C-4 (resource limits and archive safety).** The system shall enforce these limits per package: 50 MB compressed, 200 MB expanded (counted after decompression), 5,000 archive members, and 10 seconds of wall time for one artifact. The 10 seconds cover the archive check and the extraction together: the extraction gets the time the archive check left. A run that exceeds the remaining time is UNKNOWN with reason `limit`. A limit that is reached returns UNKNOWN with reason `limit`. Before it reads any member, the system shall reject the artifact if a member name is absolute, has a `..` segment, contains a NUL byte, or repeats another member's name, or if a member is a symlink, a hardlink, a device, or a fifo. The rejection returns UNKNOWN with reason `parse_error`. The system shall not write archive members to disk. The system shall run the extractor in a subprocess with an empty environment, the Python interpreter in isolated mode, the temporary directory as its working directory, and operating-system limits on CPU time, address space, file size, and open files, with core dumps off. This is POSIX only. Windows is out of scope. If the operating system limits cannot be set, the result is UNKNOWN with reason `limit`. A worker killed by a signal, whether by the wall-time kill or by the CPU, memory, or file-size limit, gives UNKNOWN with reason `limit`. A worker that reports a memory error gives UNKNOWN with reason `limit`. A worker that exits non-zero without being killed by a limit, or that prints output that is not valid, gives UNKNOWN with reason `parse_error`. The parent shall not trust the worker's `root` field until it checks that the value is a relative path with no `..` segment, no backslash, and no NUL byte, and that it resolves inside the artifact's private directory. A root that fails the check gives UNKNOWN with reason `parse_error`.

**R-C-5 (three-valued result).** The system shall report an intent check against a contract as one of three values:

- PRESENT, only when the contract is complete and the symbol is in it, or when a complete entry point of a contract with several entry points lists it (R-C-3, two entry points).
- ABSENT, only when the contract is complete and the symbol is not in it.
- UNKNOWN, in every other case: a limit, a statement the completeness rule does not model, a file that does not parse, an artifact without a wheel, no usable digest, or an error getting the data. UNKNOWN carries one typed reason, one of the seven in the glossary.

An UNKNOWN shall give BLOCK (exit 1, check `api_surface`, and the reason names the typed reason). It shall never give ALLOW and shall never give QUARANTINE. Only ABSENT gives QUARANTINE (exit 75, `mismatch_type: api_absent`, R-Q-1). A symbol that is in an incomplete contract is UNKNOWN, not PRESENT, except in the one case of R-C-3 (two entry points). This exception is the only one to the rule that UNKNOWN never allows. P-C-2 states it. This keeps v1 R-Q-2 and P-FC-3 as written. The offline snapshot uses the same three values. A package or version the snapshot does not cover is UNKNOWN with reason `not_in_snapshot`.

**R-C-6 (cache).** The system shall cache each complete contract in `contracts/` under the state directory (default `.slopseal/contracts/`). The cache key is the verified registry digest of the artifact, written as `<algorithm>-<hex>`, and never the URL. For PyPI the key is the sha256 digest. For npm it is the sha512 digest the registry published, because the registry publishes no sha256 and a sha256 key would need the download that the cache exists to avoid. The system shall check that the key is a known algorithm followed by lowercase hexadecimal before it uses the key as a file name. Each entry shall store the key, the extractor version, the export names, and a SHA-256 hash of those fields. A cache hit shall need no download and shall return within 100 ms, measured from the point where the digest is known. The system shall discard an entry, and treat the lookup as a miss, if the stored hash does not match its content, if the key does not match the file name, if the extractor version differs, or if the file cannot be parsed. The system shall store only complete contracts. It shall never store UNKNOWN or a digest mismatch. It shall write an entry only after the artifact has been downloaded and its digest has been verified against the published digest (R-C-1). A download that fails verification leaves no entry, and no entry is written before verification. This applies to the npm key (sha512) as to the PyPI key (sha256).

**R-C-7 (Contract Diff).** When an intent check is ABSENT, the system shall add the contract diff to the QUARANTINE payload: the claimed symbol (`declared_api`), the real exports (`found_apis`), and, for each miss, the nearest real symbol. The nearest real symbol is the export with the smallest Levenshtein distance to the claimed symbol, with ties broken by ascending byte order. It is written as the `missing_evidence` entry `nearest_real_symbol:<claimed>=><nearest>`, and omitted when the contract has no exports. `found_apis` is sorted and capped, and a cap that cuts it adds the entry `found_apis_truncated`. The payload shall not include a confidence number or any other number. The payload keeps exactly the field set of R-Q-3 (P-SM-4). This applies to offline and live results alike.

**R-C-8 (wiring).** In live mode, the registry adapter shall obtain exports from the Contract Check. In offline mode it shall keep reading the snapshot, and the snapshot and its checksums shall not change. The Contract Check shall run only when an intent declares an `expected_api`, so an install without an intent downloads no artifact. The install hook and the PATH shim pass no intent and shall not run it. The only network use shall be the registry metadata request and the artifact download. For each version in the snapshot, a contract built from an artifact made from that version's snapshot data shall give the same answers as the snapshot (see design, section 2.9). The registry source shall expose `contract(ecosystem, name, version)`, which returns the complete exports or UNKNOWN with one typed reason (R-C-5). The verdict shall call `contract()`, and it shall not call `exports()`. PyPI artifacts are read by the R-C-2 extractor, and npm artifacts by the R-C-3 extractor. Both run in the worker's extract mode, under the shared wall limit of R-C-4. The registry digest, artifact download, digest verification, safe archive handling, and the cache of R-C-1, R-C-4, and R-C-6 run before the extraction step. No stub remains in the live path. `LiveSource.contract()` shall match every value of `Ecosystem` exhaustively, so that a new value is a type error until it has a case. PyPI and npm are extracted (R-C-2, R-C-3). CARGO, RUBYGEMS, and GO give UNKNOWN with reason `parse_error` and the detail `no contract source for this ecosystem`, with no network request. No new reason is added, so the seven-reason rule holds. This is the decision of ruling 1 at the 2.14 review.

**R-C-9 (escalated retry).** When a retry meets an escalated quarantine and the contract for the package is UNKNOWN, the system shall return BLOCK (exit 1, check `api_surface`, typed reason), not exit 75 with `mismatch_type: api_absent`. The quarantine state is saved as before, and the retry budget is consumed. When the contract is complete, the escalation artifact is written and the payload is built as before. When the contract is UNKNOWN or a digest mismatch, no escalation artifact is written, and the BLOCK does not refer to any artifact. The BLOCK names the typed reason and a next step. The audit log entry for the decision carries the typed reason and the check name (`api_surface` for UNKNOWN, `contract_digest` for a mismatch). A test for UNKNOWN asserts exit 1, the typed reason, no artifact file, the consumed budget, and the audit entry. This corrects the v1 behavior at `_escalated_again`, which labels an unknown contract as `api_absent`.
